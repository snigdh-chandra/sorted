Why only 31 category training examples?

The inherited merchant-family split reserved all user-reviewed targets for evaluation. Its usable training set contains 31 category examples and 70 abstention examples, all with draft targets. This is the training count for this experiment, not the total data available. Reviewing the fresh set will support a new protocol with reviewed training labels.

Why were seven examples excluded?

Recovered merchant identities exposed overlap across the old partitions. Five training rows and two validation rows were excluded using identity, exact input, and related-event links. Original test membership is unchanged. Both feature versions use the same effective partitions; known group and input overlap is zero.

What changed after the parser fixes?

Features changed for 40 eligible examples. Missing merchants fell from 20 to 10. All ten remaining cases already have abstention targets; no named-category candidate lacks a merchant. Two identical-input label conflicts remain visible for review. Existing reviewed annotations were preserved byte for byte.

Read the limits

These are useful engineering checks. A fresh, independently reviewed sample and real-phone model measurements are still needed before release.

Labels and test reuse

The 97-message test includes 22 user-reviewed targets and 75 assistant-only targets. Training uses draft labels under the inherited protocol. Reviewed fields are not blanket verification of every field in a message. The corpus has already informed parser development and earlier experiments.

Threshold selection and uncertainty

Thresholds were selected on validation, using a 90% point-precision target and at least five suggestions. Merchant suggestion rules and both character classifiers failed that gate and therefore abstain in the gated view. The source-aware parser selected 0.8: 40 of 44 validation suggestions and 37 of 42 test suggestions were correct. Its test precision is 88.1%, with an approximate Wilson 95% interval of 75.0–94.8%. This does not establish 98% production precision.

Models and device performance

The experiments used character n-gram TF-IDF and logistic regression, not a fine-tuned language model. The merchant+direction artifact is 50,515 bytes; the merchant-only artifact is 49,100 bytes. Warm local Python CPU p95 was approximately 0.46 ms and 0.41 ms, respectively. Android runtime size, cold start, memory, battery, and inference latency were not measured. No model has been distilled, pruned, quantized, or deployed.

Review pending

50 fresh examples are reserved

49 are proposed category examples; one is a provident-fund contribution notice for separate movement review. Their answers are assistant drafts. They have not been used for training, threshold selection, or scoring. Business identities still need review for masked and gateway descriptors.

  1. Choose a useful example

    Start with underrepresented categories, failed or future payments, confirmed refunds, or ambiguous recipients. Include meaningful wording variants.

  2. Sanitize before sharing

    Use synthetic examples or carefully sanitized messages you have permission to share. Replace identities, account details, references, dates, and secrets locally.

  3. Label only what the message supports

    Keep cash evidence, event type, and category separate. Preserve unknown amounts. Personal account ownership and purchase purpose stay out of shared labels.

  4. Validate and open a data PR

    Copy the JSONL examples, run the local validator, and document review status and related examples. Contributions remain candidates until reviewed.
